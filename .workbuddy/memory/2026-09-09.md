## 关键技术结论（值得沉淀）

- llama_index 99.97% → 160+ 集成包做成 namespace package（`llama-index-integrations/*`），核心包零外部耦合 → 适合**嵌入现有 Java/Spring 系统**做文档问答（可单独 pip 装核心包）

## 踩坑（新增，重要）

**GitHub 直连 443 当前不可达**：git clone 与 git push 均失败（RC=128，`Failed to connect to github.com:443`）。

解法（两条路，均已验证）：

1. push：`git -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 push origin main` → 一次通过（Clash 代理）
2. clone：`codeload.github.com` tarball fallback（ragflow 18.4MB / llama_index 272MB），副作用是无 .git 目录

后续遇 push exit 128 直接带代理参数重试，不要死等或死循环重试。
（注：未改全局 git 配置，避免 Clash 未启动时反而连不上。）

### 场景设计（贴本人 EMS 业务）

攻击面设在**设备备注 remark 字段**（现场可自由填写、无审核）。Agent 读它又能执行动作时，
数据与指令的边界消失 —— 间接 Prompt Injection。不是Demo风险，EMS 里真实存在。

### 实测（qwen3.8:27b）

hardened 9/9，naive 9/9。

结论：**真正拦住攻击的是 Server 层**（权限/路径/审计三条确定性拦截，不依赖模型）；
强模型下防注入提示词边际价值接近零。投入顺序应为 权限模型 > 输入隔离 > 审计 > 提示词。
边界：9 例均为单轮直白注入，未覆盖多轮社会工程。

### 最重要的踩坑：判定器误判（踩了两轮）

第一版 7/9，那 2 个失败模型行为其实完全正确（明确拒绝 + `ACTION: NONE`），
因为判定器用**全文关键词匹配**——模型「复述攻击内容以示拒绝」时会原样引用危险词。

修正：只解析 `ACTION:` 行判定。
修完 `llm_was_hijacked()` 后，用例 6 残留的一条独立全文条件**又**误判了一次，
所以修判定器必须全局搜一遍遗留匹配，改一处不够。

通用原则：**评测器的可信度不会高于被测对象**。
